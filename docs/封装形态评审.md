## 各视角要点

### 跨项目与跨机器（可移植性 / 分发通道 / 同步与版本控制适配性）

**排序：A > C > D > B**

先把量核实清楚：核心资产只有约 10MB（components 4.0M，其中 2.3M 是 Lanyard 的 card.glb；public 3.0M；prompts 2.5M；scripts 100K），纯文本部分约 4.2MB。旁边挂着 node_modules 538M 和 .cache 133M——它俩已在 projects-sync.exclude 里，但 playground/dist 15M 没排除，会白同步/白提交。也就是说：这批东西进 git 完全无压力（忽略 dist 后 ~10MB，二进制只有 5.3MB 且几乎不变），进 rsync 也无压力，唯一不能碰的是那 671M 可再生物。

再看依赖拓扑，这是拉开差距的地方：139 个组件里 36 个零依赖；ogl 覆盖 31 个、gsap 26、three 21、motion 19；剩下 10 个包各自只服务 1 个组件——face-api.js 8.1M、mathjs 17M、lucide-react 43M、matter-js、@react-three/rapier、gl-matrix、meshline、maath、lenis、@use-gesture。按组件取用（A），典型成本是 12KB 源码 + 0~2 个包；打成一个 npm 包（B），是把这整个 21 包面拖进每个消费方。对一个 Electron 桌面端来说这不是洁癖问题，是安装包体积问题。

版本现实更致命：taptv 是 **React 18.3.1 + three ^0.184**，这个库是在 **React 19.2.8 + three ^0.180** 上验证的，且 6 个组件用 forwardRef、2 个直接把 ref 当 prop 接（React 19 才成立）。B 一发包，peerDependencies 立刻和 taptv 撞车——要么把 peer 放宽到没意义，要么装出两份 three（32M×2，且 WebGL context 会打架）。C 把自己的 package.json/lockfile 一起塞进应用树，同样要处理 hoist 和去重。只有 A 把代码落进 taptv 自己的依赖图里，撞了当场在本地改——这恰好就是用户原话「集成进去再微调」。

分发通道上还有一条硬约束：taptv 的 Windows 构建跑在 GitHub Actions 上（build-windows.yml 用 `npm install`）。私有 registry 若架在 Mac mini 192.168.31.105，GitHub runner 够不着，B 会在**发版时**炸而不是开发时炸。同理，submodule 的 URL 若只指向局域网也会让 CI checkout 失败。这直接决定了：源头必须放在两台机器和 GH Actions 都够得着的地方（私有 GitHub 仓库），不能只靠 projects-sync 的单向文件镜像——那份镜像在 Mac mini 上是**只读副本**，从设计上就不能当分发源。

资源搬运只有 2 个组件有坑，但恰好是手拷必踩的两个：Lanyard 是同目录 `import cardGLB from './card.glb'`（只拷 .tsx 直接 build 失败），FluidGlass 硬编码了 `/assets/3d/*.glb` 和 `/assets/demo/*.webp` 三条根绝对路径，在 Electron 的 file:// 下不解析。CLI 能拷贝并改写，D 会踩，B 得为 2 个组件在 tarball 里常驻 5.3MB 二进制。

最后，A 的建造成本被低估了：`prompts/index.json` 已经带 name/category/dependencies/url/bytes/props 和 byDependency 反查表，`props.json` 已经标出组件真实接收的 prop 与「幽灵 prop」——这就是一份现成且已对账的 shadcn registry。四个方案里 A 反而是元数据层最完备、离能用最近的一个。

排序理由：A 唯一同时解决「按需取依赖 + 资源随行 + 落地即可改 + 跨项目版本不撞」；C 是好的**传输层**（GitHub 私有仓库 10MB，两台机器 clone 即用）但坏的**消费模型**（submodule 进 Electron 要显式排出 asar，且 solo dev 在两台机器间维护 submodule pin 是 detached HEAD 陷阱）——正确用法是把 C 垫在 A 底下，而不是拿它当形态；D 跨机器能力为零（今天连镜像都没有），且把「哪个组件要哪些包/哪些文件」这个已经结构化好的知识重新退回人脑；B 排最后不是因为麻烦，是因为它同时违反用户诉求（拿来改）、撞版本（React 18 vs 19、three 0.180 vs 0.184）、并把发版通道绑死在一台局域网机器上。

**最容易被忽略的风险：**真正会咬人的不是「换台机器打不开」，而是**副本失去出处**。现在 139 个组件是钉在上游 commit `b9158ac`（记在 memory/project_progress.md）上的，上游还在涨组件；一旦开始往 taptv、eas-term、bizone-website 里拷，半年后没有任何机制能回答三个问题：这份 Orb 是哪个 commit 的？我改过它没有？上游后来修过它没有？而这个库本身还刻意保留了已知缺陷不修（LetterGlitch 的 cleanup 只 cancelAnimationFrame 不清 resize 定时器，为了跟上游字节一致），意味着上游修了你也不知道自己哪几个项目里躺着旧版。没有出处戳，方案 A 会在两台机器上、六个月内退化成方案 D，而且比 D 更糟——D 至少你知道自己是手拷的，A 会给你一种「我有工具管着」的错觉。第二重风险是这个目录**今天根本不在同步链路上**：`projects-sync.sh` 的 SRC 是 `~/Biily/Projects`，而库在 `~/Biily/资产收集/交互动效`，Mac mini 上现在一个字节都没有。

**不管选哪种都必须具备：**
- 产物自带出处戳：拷进目标项目的每个组件要落一条记录（组件名 + 上游 commit + 原始源码 hash + 拷入日期），并有一条命令能跨项目回答「哪些副本已被我改过 / 哪些上游已更新」。没有这个，任何形态半年后都退化成手拷。
- 按组件解析依赖并只装它要的（直接复用 prompts/index.json 的 byDependency），装之前先读目标项目 package.json 做版本比对——react/three 这类已存在且版本不同的必须显式报出来让人决策，不能静默安装或静默跳过。
- 源头放在两台机器和 GitHub Actions 都够得着的私有 git 仓库，不依赖 192.168.31.105 或本机绝对路径；同时把 node_modules(538M)、.cache(133M)、playground/dist(15M) 排除在版本控制与同步之外，并把项目纳入（或另建）一条真正覆盖 ~/Biily/资产收集 的同步路径。

### 日常取用体验（想起某个效果 → 找到 → 弄进项目 → 跑起来 → 改成自己的）

**排序：A > D > C > B**

我按「新项目要用其中 3 个效果」实际走了一遍，摩擦根本不在「拷文件」这一步——139 个组件全是单文件、无内部互引（全库唯一的相对 import 只有 Lanyard 的 ./card.glb 和 ./lanyard.png），中位数 278 行 / 6KB，拷 3 个 = 20KB，手拷 30 秒。所以 B 和 C 想解决的「分发」压根不是痛点。真正的摩擦全在「跑起来」和「不被冲掉」上，而这两件事只有 A 能自动化：

**（1）依赖清单是错的，而且是无声的错。** 我拿 AST 把 139 个组件的真实 import 和 index.json / prompt 里的 `### Dependencies` 对了一遍：11 个对不上，10 个是漏报。最狠的是 Silk——prompt 里连 `### Dependencies` 这一行都没有，实际要 `@react-three/fiber` + `three`（一整套 3D 栈）；PillNav 漏 `react-router-dom`（在 Electron 里塞个 router 依赖是要出事的）；FadeContent / StickerPeel 漏 gsap，GradientText 漏 motion，MagicRings 漏 three，Ballpit 漏 gsap，GridScan 漏 postprocessing，CardNav / Carousel 漏 react-icons；GradualBlur 反过来多报了 mathjs（白装）。playground 列表里那一栏「依赖」用的也是这份数据，所以选型台也在骗你。上游 propData 会一直漂，这不是修一次就完的。而 `scripts/check-deps.mjs` 已经有现成的 AST 机器，A 里接上就是确定性的正确；D 你只能照着错的清单装，报错了再回头猜。

**（2）资源跟不跟得走，差别很大。** 只有 2 个组件真的带资源，但每个都是坑：Lanyard 要同目录的 card.glb（2.4MB）+ lanyard.png，而它的 prompt 原文写的是「You MUST have card.glb and lanyard.png … can be downloaded from the repo's files」——线上取用要你自己去 GitHub 翻，本地库里明明已经躺着了，A 一条命令就能带走，这是本地化最大的红利之一。FluidGlass 硬编码了 6 个 `/assets/3d/*.glb`、`/assets/demo/cs*.webp` 根绝对路径（三张 webp 各 650KB），Electron 打包后走 file:// 协议根绝对路径直接挂，需要在拷贝时重写前缀。再加上 `assetsInclude: ['**/*.glb']`、`declare module '*.glb'` 这些 vite / TS 配置，prompt 里只有 Lanyard 一个组件顺带提了。这些都是「每次都要重新想起来」的税，A 收一次，D 收无数次。

**（3)「改动被冲掉」的真实形态和描述里问的不一样。** A/C/D 都是代码进你的项目，你的改动不会被上游冲掉。真正被冲掉的是**你想给库本身打的补丁**：`scripts/build-prompts.mjs:513` 是无条件 `writeFileSync` 覆盖 `components/`，加上 CLAUDE.md 硬规则要求与上游字节一致——memory 里已经有一条实证：LetterGlitch 的 rAF 清理泄漏（会污染下一个组件）查清了但「没修，因为 components/ 要与上游保持字节一致」。也就是说现在**没有任何地方能存放你的修复**，每次刷新上游全丢。这个洞只有 A 能补（拷贝时应用补丁层），D 补不了，C 更糟（改在 submodule 里，submodule update 时冲突）。

**为什么 D 排第二而不是垫底：** D 不是「什么都没有」，playground 已经把「找到它」这一环做得很好了——搜索（名称/类目/依赖）+ 实时预览 + 自动参数面板 + 三个复制按钮（复制用法/源码/Prompt），而且「复制用法」只输出与默认值不同的 prop，正好是你调完手感之后最想要的那段。这一环 A/B/C/D 都不改变，是共同底座。D 的成本只是每次重复交那笔依赖税和资源税。唯一的 step-0 摩擦：package.json 里**没有 scripts 字段**，连 `npm run dev` 都不存在，几周才用一次的工具得记得敲 `npx vite`——这个不管选哪个形态都该顺手补上。

**C 垫在 B 之上但明显差：** 为了用 3 个效果，把 4MB / 139 个组件整个 clone 进目标项目，Electron 打包时还得排除；改一行要在 submodule 里 commit、detached HEAD、再回主仓库 bump 指针——这套仪式对一个自用的独立开发者是纯负担。

**B 最差，而且是直接违背诉求。** 用户原话是「集成进去再微调」，npm 包里的代码你改不了，只能靠 props 和 fork。更阴的是 Tailwind：95/139 个组件用 Tailwind class，包一旦装进 node_modules，Tailwind v4 默认不扫 node_modules，组件会**静默地没有样式**——不报错，就是长歪，排查起来极费劲。再叠上 21 个第三方包的 peer/optional 依赖矩阵、glb 资源还得另外拷进 public、以及给自己一个人维护版本号的仪式感，收益是负的。

**最容易被忽略的风险：**组件的**默认值里埋着 33 处外网资源**，取用时不报错、开发机联网时一切正常，等打包进 Electron 交给离线用户才炸——而他主力项目就是 Electron 桌面应用。实测（scripts/check-deps.mjs）：CircularGallery / DecayCard 的 picsum 图、DomeGallery / Stack 的 unsplash 图、CircularGallery / ASCIIText / TextPressure 的 Google Fonts、GridScan 运行时去 jsdelivr 拉 face-api 权重；另外 StaggeredMenu 的默认 logoUrl 指向 `/src/assets/logos/reactbits-gh-white.svg`，这个文件本地库里**根本不存在**（只在 .cache 的上游仓库里），拷过去就是个 404 破图。这套「哪些默认值必须换掉」的知识现在只活在 playground 的 preview-overrides.json 和 registry 的 OVERRIDES 里（也只是为了让选型台离线跑通），取用路径完全没接上——你在选型台看得好好的，拷进项目却带走了一堆外链。同类的隐性知识还有 draco 解码器：`playground/main.jsx:15` 有一行 `useGLTF.setDecoderPath('/draco/')` 加一句注释说明「离线时那两个请求会挂住」，用 ModelViewer 加载 draco 压缩模型的人必须知道要连 public/draco/ 一起搬，但没有任何 prompt 或索引提过这件事。取用形态必须把这类「离线化改写 + 隐性前置条件」做成拷贝时的一等公民，否则本地库最大的卖点（离线可用）在取用那一刻就漏光了。

**不管选哪种都必须具备：**
- 依赖清单必须从源码 AST 推导，不能信 index.json / prompt 的 Dependencies 行——实测 139 个里 11 个对不上（Silk 连 Dependencies 那行都没有，实际要 @react-three/fiber + three；PillNav 漏 react-router-dom；GradualBlur 多报 mathjs）。scripts/check-deps.mjs 已有现成机器，顺便把 gsap 插件注册、three/examples/jsm 子路径（OBJLoader 目前解析不到）这类坑一并提示，并把修正后的依赖回写给 playground 列表显示。
- 资源和配置随组件走并做路径重写：Lanyard 的 card.glb(2.4MB)/lanyard.png 同目录带走，FluidGlass 的 6 个 /assets/** 拷进目标 public 且前缀可改（Electron file:// 下根绝对路径必挂），用 GLTF 就带上 public/draco 并 setDecoderPath；同时自动补 vite 的 assetsInclude: ['**/*.glb'] 和 declare module '*.glb' 的 TS 声明。外链默认值（33 处 picsum/unsplash/Google Fonts/jsdelivr）在拷贝时替换成内联或本地资源。
- 取用入口接在 playground 上、并保留一个本地补丁层：选中组件时连同你刚调好的那组参数一起产出（现有「复制用法」已经只输出 diff，是对的），别让人回去翻 components/ 目录；补丁层是必需的，因为 build-prompts.mjs 会无条件覆盖 components/，像 LetterGlitch 那个已查清但「为保持字节一致而没修」的 rAF 泄漏，只能以拷贝时应用的补丁形式存在。

### AI 协作工作流（Claude Code 介入的顺畅度：怎么发现、怎么选、怎么落地、信息会不会骗人）

**排序：A > D > C > B**

**A 第一**，因为它把 AI 最不擅长、最容易漏的那部分变成确定性操作。我核实过的漏点全是机械性的：只有 Lanyard 用同目录 import（`from './card.glb'`，还要求目标项目改 vite assetsInclude 和加 declare module），只有 FluidGlass 硬编码 `/assets/3d/lens.glb`（这个在 Electron 打包后走 file:// 协议会直接失效，dev 好使、装出来的画板不好使，属于最坏的一类 bug），draco 解码器路径只在 playground/main.jsx 的注释里交代过。这些一次性写进 CLI，之后每次集成都对；靠 AI 每次读 12.7KB 的 prompt 现推，每次错法都不一样。另一个被低估的收益是 token：prompt 平均 12.7KB、最大 44KB（LiquidEther），内容 90% 是源码副本；AI 走 CLI 只需要「列表 → 挑名字 → 跑命令」，把 3.5k~12k token 的阅读换成几百 token，139 个组件的库这个差别是量级的。CLI 还天然是写出处戳和「改过没有」对账的地方。

**D 第二**，不是因为它好，是因为它诚实。AI 拿到绝对路径就能 cp，能直接读 .tsx 源码（源码是唯一没骗过人的东西，CLAUDE.md 第 2 条硬规则就是这么定的），不引入任何新的失真层。它缺的恰恰就是 A 补的那些：漏资源、漏 vite 配置、漏 draco、没出处。所以 D 是「A 减去确定性」，而不是另一条路。

**C 第三**，submodule 在 AI 手里额外扣分。最实际的问题不是 detached HEAD（虽然 agent 确实经常在这上面翻车），而是它给 AI 提供了一条「看起来能用」的捷径：直接 `import Silk from '../vendor/react-bits/components/Backgrounds/Silk'`。这条 import 编译得过、跑得起来，然后用户说「微调一下」，AI 就去改 submodule 里的文件——那是所有项目共享的一份，改画板顺手改坏别的项目，而且下次 upstream 更新时冲突。这和用户原话「把代码集成进去再微调」是直接对立的。它唯一比 D 强的是 index.json/props.json 在目标项目里离线可达，但这个用一条 CLI 命令就能给到。

**B 最后，且差距很大。** 三个硬伤：① 组件是拿来改的，这不是抽象立场，是这个库里已经记录在案的现实——LetterGlitch 的清理函数只 cancelAnimationFrame 没清 resize 定时器（会污染下一个挂载的组件）、StaggeredMenu 的 logo 默认值指向 `/src/assets/logos/reactbits-gh-white.svg`（本地根本没这文件）、ScrollStack 靠 `.scroll-stack-card` 这个 class 抓卡片、TextPressure 默认字体走 Google Fonts 离线挂掉。这些在 D/C/A 里是 AI 改两行的事，在 B 里全变成「包一层 wrapper 或 patch-package + 发版」。项目自己都因为「components/ 要与上游字节一致」而拒绝修 LetterGlitch，说明本地库的定位就是镜像，微调必须发生在下游——npm 包正好把下游的手绑住了。② 21 个第三方依赖但每个组件只用一两个：做成一个包就得让画板为了一个 Silk（只要 ogl）背上 three + rapier + matter-js + face-api 的 peer 关系，拆成 139 个小包对单人维护是灾难。③ 对 AI 最直接的伤害是可读性倒退：代码进了 node_modules，AI 读得到但不该改，props 的真值（props.json 里那份 `actualProps` / `phantomProps`，实测比文档可信）也被埋进包里，链路反而比现在更绕。

另外两个会拖慢 AI 的具体现状，顺带记一下：`prompts/index.json` 里 139 条的 `source` 字段全是上游路径 `src/ts-tailwind/Animations/AnimatedContent/AnimatedContent.tsx`，在本地一条都解析不到（本地路径在 props.json 里，是 `Animations/AnimatedContent.tsx`）——AI 拿索引去找文件会 100% 落空一次再自己纠正；`props.json` 是单个 491KB 的文件（约 13 万 token），AI 无法整读，必须切成按组件的分片或提供查询命令，否则「真值元数据」在实践中等于取不到。

**最容易被忽略的风险：**最容易被忽略的是 **prompts/ 在 AI 链路里的定位错了**——我实测 139/139 个 prompt 里嵌的源码与 components/ 下的 .tsx 逐字节相同，也就是说 prompts/ 是同一份代码的第二副本，而且是 AI 最可能当成「权威集成说明」去读的那一份。问题在于它照抄的是上游文档，不是本地事实：① 6 个组件的 props 表里有幽灵 prop（AnimatedContent 文档写 `dissappearAfter`、源码解构 `disappearAfter`；GridDistortion 的 `imgageSrc`；Ferrofluid 两个重名 `backgroundColor`），AI 照表写参数会静默落进 `...props` spread 到 DOM，画面不动、控制台不报错，是最难查的那类 bug；② Lanyard 的 prompt 第 32-33 行写着「从 repo 的 src/assets/lanyard 下载 card.glb」——指向 GitHub，而这两个文件明明就躺在本地 `components/Components/`，AI 会去联网、或者干脆跳过；③ SpecularButton 的依赖行是 `npm i ogl`（上游笔误，prompt 为保真照抄）。更远一点的坑：整个库没有任何「这份代码取自哪个上游 commit」的戳会跟着代码进目标项目（`prompts/.meta.json` 记着 b9158ac，但拷出去的 .tsx 上什么都不带）。上游还在涨，半年后 AI 被要求「更新一下画板里那个 Silk」，既不知道当初取的是哪一版，也不知道用户后来微调过哪几行——只能整段覆盖，把微调冲掉。

**不管选哪种都必须具备：**
- 机器可读的「组件 → 它到底要什么」清单，且必须由 build 脚本自动生成：npm 依赖(带版本)、同目录资源(Lanyard 的 card.glb/lanyard.png)、public 绝对路径资源(FluidGlass 的 /assets/3d/*.glb)、构建配置改动(vite assetsInclude + declare module '*.glb')、three 系组件要的 draco 解码器路径设置、以及 3 个运行时联网的组件(FluidGlass/FlyingPosters 拉 jsdelivr 字体解析器、ASCIIText 拉 Google Fonts、GridScan 的 face-api 拉 CDN 权重)。这些事实项目里全都有，但散在 build-prompts.mjs 的 publicAssets()/importedAssets()、playground/main.jsx 的注释、和可被清空的 .cache/network.json 里——index.json 的 139 条记录一个 assets 字段都没有，AI 读不到。
- 出处戳 + 一条对账命令：集成进目标项目的每份代码顶部带上游 commit / 组件名 / 取用日期，并能一条命令回答「我这份改过没有、上游变了没有」。没有这个，AI 在跨项目、跨半年的场景下无法安全更新。
- 能用自然语言检索的选型入口：139 个组件名(Silk / Balatro / DarkVeil / Ferrofluid / Prism)几乎没有语义，index.json 里只有 name/category/dependencies/url，一个描述字段都没有。AI 拿到「给启动页加个暗色流动背景」根本无法映射到候选。.cache/shots/all/ 那 139 张截图正是生成一句话视觉描述 + 标签的原料，但它现在躺在一个名字就叫 cache 的目录里。

### 实现成本与风险（要动手把它做出来的人）

**排序：A > C > D > B**

先说 A 为什么第一：它的增量成本非常低，因为材料几乎全是现成的。index.json 已经有 139 条 name→category→源码路径→站点 URL 的映射；build-prompts.mjs 里的 publicAssets()/importedAssets() 是专门为「拷源码时资源要跟着搬」写的，已经在 139 个组件上跑过；check-deps.mjs 用 @babel/parser 扫出的 35 个真实说明符（含 three/examples/jsm/... 这类子路径）就是「这个组件到底要装什么」的准确答案。把这些拼成一个 bin/rb-add.mjs（解析名字→拷 .tsx→拷两类资源→算依赖并打印 npm i→盖 MIT 头→打警告），我估 200-300 行，一半是搬现有代码，含往 taptv 里做一次真实冒烟验证，半天以内。而它替掉的，正是这个仓库自己已经用血写在 README 里的四个坑：忘拷同目录 .glb → 500；忘拷 public 资源 → 组件拿到 index.html 报 "Unexpected token '<'"；依赖表漏列 → 白屏；默认 props 引外链 → 离线破图。每个坑手工重踩一次都是十几分钟起。

C 排第二，但理由和大家想的不一样：submodule 本身没什么价值——139 个组件 + prompts + playground 全塞进 taptv 仓库，Electron 打包还得写排除规则，塞完你还是要手工复制粘贴，比 D 只多了个「能拉更新」。真正有价值的是**这个库现在根本不是 git 仓库**（git status: not a repository）。上游还在涨组件，重跑 fetch-repo.sh + build-prompts.mjs 之后，没有版本控制你就看不出这次 139 个 .tsx 里哪几个变了、变在哪——而这恰恰是「字节级一致」这条硬规则唯一可验证的抓手。所以 C 该做，但它是 A 的地基（git init + .gitignore 排掉 node_modules 538M / .cache / playground/dist，剩下 10MB 左右），不是 A 的替代品。

D 排第三：成本确实是零，但它的代价是把上面那四个坑变成每次集成都要重踩的固定税，而且踩的时候人在另一个项目的上下文里，手边没有这份 README。用户原话是「拉取的时候直接把代码集成进去再微调」——D 是能干这事，只是每次都要自己记得 Lanyard 有两个同目录资源、FluidGlass 有六个 public 资源、CardNav 的依赖表是错的。

B 排最后，而且是明显最后。成本最高：要建 build 链（TS→JS + d.ts）、要处理 .glb 打包、要决定 21 个第三方包怎么摆——做成一个胖包，就为了用一个纯 CSS 的文字动效把 three/ogl/matter-js/face-api.js 全拖进 Electron 的 node_modules 和 asar；做成 139 个子包，一个人维护根本不现实。同时它在这个具体项目上是**功能性失败**：97 个组件带 Tailwind 类名，发布成 npm 包后宿主的 Tailwind content glob 默认不扫 node_modules，而 taptv 压根没有 Tailwind；three 写成 dependency 就双实例，写成 peer 就得手工维护 21 条 peer 范围。最要命的是它和诉求正面冲突——上游 react-bits 的定位就是 copy-paste、组件是拿来改的，包进 node_modules 之后想微调只能 patch-package 或 fork。另外只有 B 会把「自用」变成「分发」，MIT 的署名义务从「应该做」变成「必须做」，而现在库里连一份 LICENSE 都没有。花最多的力气，买一个更差的结果。

**最容易被忽略的风险：**Tailwind 缺口 —— 四个方案的讨论里没人提，但它是第一次真集成时必然踩的。我数了：139 个组件里 97 个 className 带 Tailwind 工具类（absolute/flex/w-full/overflow-hidden 这类），而主力项目 taptv（bizone-canvas 1.21.13）的 package.json 里既没有 tailwindcss 也没有 typescript，vite.config 是 .js。TS 语法不是问题（Vite 用 esbuild 转，不装 typescript 也能构建，只是没类型检查），但 Tailwind 类名在没有 Tailwind 的宿主里就是一串无效字符串：组件正常挂载、控制台干干净净、画面布局全塌。这个症状最容易被判成「这个组件坏了/这个库不行」，而不是「宿主缺 Tailwind」，然后开始在组件里瞎改。所以取用工具必须在写文件之前就检测宿主有没有 Tailwind，命中 97 个里的组件时直接把这句话打出来，并给两条明路（给宿主加 Tailwind，或按需手改这一个组件的 className）。第二个同类风险是 three 双实例：库锁 0.180、taptv 是 ^0.184，如果走 B（npm 包）把 three 写成 dependency 而不是 peer，就会出经典的 "Multiple instances of Three.js being imported"，表现是材质/渲染莫名其妙失效，极难定位。

**不管选哪种都必须具备：**
- 取用动作必须一次性解决三件事：同目录 import 的静态资源（只有 Lanyard，card.glb 2.4MB + lanyard.png）、绝对路径引 public 的资源（只有 FluidGlass，6 个文件）、以及按 AST 算出来的真实依赖（不能信 index.json/props.json 里从 propData 抄来的 dependencies，README 自己记着 CardNav 漏了 react-icons）。这三段代码在 build-prompts.mjs:223-241 / 515-539 和 check-deps.mjs:32-68 里已经写好并跑通了，抽成一个 lib 直接复用，别重写。
- MIT 义务要在「拷进目标项目」这一刻完成：每个落地文件顶部盖一行出处（github.com/DavidHDev/react-bits + commit b9158ac + MIT），目标目录放一份 LICENSE-react-bits.md。现在整个库根目录没有任何 LICENSE 文件、139 个 .tsx 里零署名，只有 prompts/.meta.json 里一句 license 字段。上游 LICENSE.md 就躺在 .cache/react-bits-main/ 里，cp 一下的事。注意盖章只能盖在输出侧，components/ 本体要保持与上游字节一致（CLAUDE.md 硬规则）。
- 取用前对宿主项目做体检并出警告，别默默拷完就说成功：宿主有没有 Tailwind、three 版本是否与库里的 0.180 冲突、vite 的 assetsInclude 有没有 .glb、以及这个组件的默认 props 会不会去拉外链（check-deps 实测 33 处 picsum/unsplash/fonts.googleapis/face-api CDN，离线 Electron 里必然是破图或挂住）。这几条判断加起来不到 40 行，但省掉的是每次集成半小时的瞎找。

### 长期维护成本（一年后这套东西还能不能用、同步上游的代价、本地微调的命运）

**排序：A > D > C > B**

我核实到的几个事实决定了这个排序：

**1. `components/` 139 个文件与上游 `src/ts-tailwind/<类目>/<名>/<名>.tsx` 逐字节一致（我全量 cmp 过：same=139 diff=0），而且项目规则明确禁止在这里改动。** memory 第 51-52 行有实证：LetterGlitch 的清理函数只 cancelAnimationFrame、没清 resize 定时器，卸载后残留的 rAF 会打到下一个组件（表现为 Lightfall 报错）—— 这个已定位的 bug **被明确决定不修，理由就是"components/ 要与上游保持字节一致"**。也就是说，这个库今天**没有任何容纳本地微调的位置**。微调必然发生在下游项目里。这不是缺陷，反而是正确的选择（保住了"重跑管线 = 干净覆盖"这条路），但它直接推出一个结论：**评估形态时，不要问"我的改动怎么合并回来"，要问"我的改动在下游怎么被记住"。**

**2. 同步上游的代价，四种形态几乎完全一样，因为同步是靠管线不是靠分发渠道。** `fetch-repo.sh` 拉 tarball → `build-prompts.mjs` 解析 → 覆写。这个成本 A/B/C/D 都要付。所以选型的差异**根本不在同步侧，全在"同步之后我的下游怎么办"侧**。这一点直接把 C 打下去了：submodule 的卖点是 `git pull`，但这里 pull 到的不是上游更新，只是我自己上一次跑管线的结果 —— 它没有省掉任何一步，却换来一个真实的坑：库文件躺在 app 仓库里但归属另一个仓库，改还是不改语义暧昧，改了就是 detached HEAD 上的孤儿提交，下次 pull 打架。这正是全局规范里说的"补丁摞补丁、测试好使过段时间又坏"的同款结构。

**3. buildPrompt 的耦合面比"复刻了一个内部函数"要宽得多。** 我读了脚本：它不只抄 `TabsLayout.jsx:63-118`，还硬依赖上游的**仓库结构**——`src/demo/<类目>/<名>Demo.jsx` 必须存在且 `propData` 是纯字面量数组（`evalNode` 遇到任何非字面量直接抛）、`src/constants/Categories.js` 里 `CATEGORIES` 必须是字面量（否则连站点 URL 都拼不出来、直接 throw）、6 个 vite 别名路径、`__src_tsTailwind` 目录布局。上游只要把 propData 改成从 JSON 引入、或者调整一次目录，管线就成片失败。**但这类失败是响的**（脚本非零退出并列出失败文件）。真正需要防的是它失败时已经把文件写坏了 —— 见 keyRisk。

**4. 依赖分布强烈支持 A、强烈反对 B。** 实测 139 个组件平均 0.90 个第三方依赖，**36 个零依赖，91 个只有 1 个**，只有 6 个 ≥3。A 的语义是"拉一个组件、装它自己那 1 个包"；B 的语义是"为了用 ShinyText（零依赖）而面对一个声明了 21 个 peer dep 的包"。而且依赖耦合已经在咬人了：`node scripts/check-deps.mjs` 当场报 **ModelViewer 引用的 `three/examples/jsm/loaders/OBJLoader` 在当前 three@0.180 下解析失败（MODULE_NOT_FOUND）**—— 这是活的、今天就存在的版本耦合断裂。A 形态下这只影响拉了 ModelViewer 的那一个项目、且只在拉取当天暴露；B 形态下一次 three 升版把所有下游一起打穿。加上主力项目是 Electron（打包后 npm link 的陈旧产物问题是经典坑），B 是四个里唯一**既不降低同步成本、又新增一整套发版纪律、还和"组件是拿来改的"这个前提正面冲突**的方案。它的唯一优势（集中修复自动传播）在这里几乎不值钱：使用者一个人、下游基本一个项目、而且组件是**故意要改散**的（40K 的 shader 单文件、硬编码颜色、靠 `.scroll-stack-card` 这种 class 选择器抓 DOM）。

**5. D 的成本不是零，是"每次都手工付一遍，而且知识不在手边"。** 我查到最典型的一例：`useGLTF.setDecoderPath('/draco/')` 这行救命代码在 `playground/main.jsx:15`，理由写在它上面的注释里 —— 也就是说"用 FluidGlass/Lanyard 这类加载 .glb 的组件时，离线环境必须自带 draco 解码器"这条知识**只存在于 playground 的一行注释里，不会跟着任何一次复制粘贴走**。同类还有 33 处硬编码远端资源（picsum/unsplash/fonts.googleapis/face-api CDN 权重），只有跑 check-deps.mjs 才看得到。这些在 Electron 离线场景下**不是构建报错，是运行时黑屏** —— 排查成本远高于当初写清单的成本。而且 memory 第 39-48 行显示这些坑在 playground 铺开时**已经真实踩过一轮了**。D 等于选择明年再踩一遍。

**为什么 D 仍排在 C 前面**：D 至少语义干净——库是库，项目是项目，拷过去就是我的代码，没有归属歧义。C 把一个不受本地 commit 管辖的目录塞进 Electron 应用仓库，换来零同步收益，还要额外维护 prompts/(2.5M)、playground/(15M dist) 的打包排除规则。C 里唯一正确的东西是"用 git"，但那是所有形态的地基，不该当作取用渠道。

**A 排第一，还有一条工程量上的实据**：它需要的零件这个仓库**基本已经写好了，只是没落盘**。index.json 已有 per-component dependencies；build-prompts.mjs 的 `importedAssets()` / `publicAssets()` 已经在逐组件解析同目录资源和 public 绝对路径资源（第 515-539 行），只是结果扔进了一个扁平的 `assetsCopied` 日志数组、没写进 index.json；check-deps.mjs 已经能 AST 扫出真实 import 并验证子路径可解析。补一个 per-component 清单字段（约 30 行）+ 一个拷贝 CLI（150-200 行，本质是按清单复制文件、打来源注释、打印 `npm i xxx`），就完事了。**它是四个方案里唯一能把"已经踩过的坑"固化成每次都自动执行的检查、而不是留在 README 和注释里等人想起来的形态。**

**最容易被忽略的风险：****这套东西现在根本没有版本基线，所以「同步上游」这个动作是不可审查的。** 我在 `/Users/biily/Biily/资产收集/交互动效` 跑 `git rev-parse --show-toplevel` 一路向上到 $HOME 都是 `not a git repository` —— 全库没有任何版本控制。而 `scripts/build-prompts.mjs` 是**边跑边就地覆写** `components/` 和 `prompts/`（第 507、513 行直接 writeFileSync），**从不删除上游已移除的文件**（全脚本无 rmSync/unlink），而且 `process.exit(1)` 在第 666 行、也就是文件**全部写完之后**才执行。三件事叠加的后果是：上游一年后必然改过，你重跑一次管线，139 个文件同时被改写，其中若有 1 个 demo 解析失败，你得到的是一棵「一半新一半旧、还混着已下架组件残留」的树，**而且没有 diff 可看、没有回滚可做、分不清哪一处是上游改的哪一处是自己改的**。大家的注意力都会放在「buildPrompt 会漂移」上，但那个风险其实是**响的**：`verify-against-site.mjs` 会当场对账失败、脚本会非零退出、README 第 193 行还专门写了应对。真正会咬人的是**静默的内容漂移**——没有基线，你连「这次同步到底动了什么」都答不出来。这一条对 A/B/C/D 四种形态一视同仁，是选型之前就必须先补的地基。

**不管选哪种都必须具备：**
- 立刻把库本身纳入 git，并把 regeneration 改成可 diff、可回滚：生成到临时目录 → 全部成功再原子替换 → 同步删除上游已移除的文件 → 失败一个字节都不落盘。同时给上游每个 commit 打一条基线 tag。没有 diff，「同步上游」就只是「重新下载一遍并祈祷」。
- 把每个组件的「完整取用清单」变成落盘数据而不是脑子里的知识：源码文件 + 同目录资源（Lanyard→card.glb 2.3MB + lanyard.png）+ public 资源（FluidGlass→3 个 .glb + 3 张 .webp）+ 用 useGLTF 就必须带的 public/draco（1MB，且要 setDecoderPath）+ AST 扫出的真实 import（含 three/examples/jsm/... 这类子路径深引用）+ 已知会外链的远端 URL。这些数据 build-prompts.mjs 第 515-539 行已经算出来了却只当日志丢掉，check-deps.mjs 也已经能算，现在 index.json / props.json 里一个字段都没有。
- 拷出去的每份代码带来源标记（组件名 + 上游 commit SHA + 拉取日期，写成文件头注释）。这是一年后唯一能做三方 diff 的机制：上游新版 / 我当初拉的那版 / 我改成的样子。没有它，「本地微调」在下一次同步时就是一笔糊涂账，只能靠记忆。

## 综合裁决

### 推荐

A 为主 + C 只取「git 化」这一层做地基 + D 保留为兜底，B 明确否决。

具体形态：一条 `node scripts/add.mjs <组件名> --to <目标目录>`，把源码 + 关联资源拷进目标项目、盖出处戳、打印要装的包、并在写文件之前对宿主做体检警告。库本身 git init 拿到可 diff 可回滚的基线，但**不做 submodule**。playground 现有的三个复制按钮原样保留，永远是手工兜底路径。

### 理由

五位评审的排序一致到罕见：**A 全票第一，B 全票最后**，分歧只在中间的 C/D（3:2）。所以主形态没有悬念，值得说的是理由和边界。

A 第一的硬理由不是"拷文件方便"——拷文件本来就不难（139 个全是单文件、无内部互引、中位 6KB，手拷 30 秒）。A 的价值全在**把已经用血踩出来的坑固化成每次自动执行的检查**：忘拷同目录 .glb → 500；忘拷 public 资源 → 组件拿到 index.html 报 "Unexpected token '<'"；依赖表漏列 → 白屏；默认 props 引外链 → 离线 Electron 里破图。这四条你的 README 里全写着，但写在 README 里的知识不会跟着复制粘贴走。

而且 A 的增量成本极低，因为零件基本已经写好了，只是没落盘：`/Users/biily/Biily/资产收集/交互动效/scripts/build-prompts.mjs:513-539` 的 `importedAssets()` / `publicAssets()` 已经在 139 个组件上跑通了同目录资源和 public 绝对路径资源的解析，结果却扔进一个扁平日志数组；`scripts/check-deps.mjs` 已经用 @babel/parser 能扫出真实 import 并验证子路径可解析。补一个 per-component 清单字段 + 一个 200-300 行的拷贝脚本，一半是搬现有代码。

B 全票垫底不是因为麻烦，是**功能性失败**。我实测确认了那位评审的发现：94/139 个组件带 Tailwind 工具类，而 taptv 的 package.json 里既没有 tailwindcss 也没有 typescript。包一旦进 node_modules，Tailwind v4 默认不扫 node_modules，组件会静默地没有样式——挂载成功、控制台干净、布局全塌。这个症状 100% 会被误判成"这个库不行"。再叠上 three 双实例（库 ^0.180 / taptv ^0.184）和"组件是拿来改的"这个前提，B 是花最多力气买最差结果。

真正被低估、五位里只有一位提到而我实测坐实的风险是：**这套库是在 React 19.2.8 + Tailwind 4 + three 0.180 上验证的，主力项目 taptv 是 React 18.3.1 + 无 Tailwind + three 0.184。** 也就是说 CLI 的第一次真实使用大概率会"拷贝成功但画面塌"。所以体检警告不是锦上添花，是 P0——它是唯一能防止你把"宿主缺 Tailwind"误判成"组件坏了"然后开始瞎改组件的东西。ScrollVelocity / GradualBlur 更阴：它们把 ref 当普通 prop 接（React 19 才成立），在 React 18 里 React 会把 ref 吃掉，props.ref 是 undefined，不报错就是不动。

### 分歧与裁决

**分歧一：C 排第二还是第三（3:2）—— 这是假分歧，拆开就没了。**
投 C 第二的两位（跨项目视角、实现成本视角）在正文里都明写了"C 的价值是 git 地基，不是 submodule 消费模型"；投 D 第二的三位反对的也全是 submodule 那套仪式（detached HEAD、改动归属暧昧、Electron 打包排除规则）。裁决：**git 化立刻做，submodule 否决**。C 从来就不该当作取用渠道。

**分歧二：要不要做「本地补丁层」—— 真分歧，我站反对方。**
日常取用视角要求拷贝时应用补丁层，用来存放对库本身的修复（点名 LetterGlitch 那个已查清但因"字节一致"没修的 rAF 泄漏）；长期维护视角明确反对，说"这个库今天没有容纳本地微调的位置，而且这是正确的选择"。
裁决：**不做补丁层。** 补丁层要维护 diff 上下文，上游一动补丁就烂，而受益面目前是 139 个里的 1 个。替代方案便宜得多：建一个 `scripts/known-issues.json`（几条记录），拷贝时命中就打一句警告，让你在下游自己改两行。保住 `components/` 与上游字节一致这条规则很重要——它是"重跑管线 = 干净覆盖"的前提，破了以后每次同步都是糊涂账。

**分歧三：外链默认值是「拷贝时自动替换」还是「只警告」—— 我拆成两类。**
取用体验视角要自动替换成内联/本地资源；实现成本视角要只出警告。
裁决：**改路径的自动做，改内容的只警告。** FluidGlass 那 6 个 `/assets/**` 根绝对路径必须在拷贝时按目标项目重写前缀（Electron file:// 下不重写必挂，且这是纯机械转换）；但 33 处 picsum/unsplash/Google Fonts/jsdelivr 默认值只列出「哪个组件、哪个 prop、哪个 URL」让你自己换。理由：`playground/preview-overrides.json` 里那些示例数据是为选型台离线跑通造的，不是你目标项目想要的画面，自动替换会往你仓库里塞一堆你没写过也不想要的 data URI。

**分歧四：跨机器分发的紧迫性 —— 我判定为假需求，降级。**
跨项目视角要求"源头放在两台机器和 GitHub Actions 都够得着的私有 git 仓库"，理由是 taptv 的 Windows 构建跑在 Actions 上。
裁决：**这条只对 B 才是硬约束，对 A 不成立。** A 是把代码拷进目标项目，CI 拉的是 taptv 自己仓库里的代码，跟这个库没有任何关系。本地 git 已经解决了真问题（可 diff 可回滚）。等真的有第二台机器要用再推私有仓库，别现在建。

**我要额外加一条五位都没充分权重的：Tailwind + React 版本缺口是第一优先级，不是收尾工作。** 见 why。

### 明确不做

- 不要发 npm 包 —— 任何形式，包括本地 npm link 和 Mac mini 上的私有 registry。三条硬伤已实测坐实：94/139 组件带 Tailwind 类且 taptv 没装 Tailwind（进 node_modules 后静默无样式）；three 写 dependency 就双实例、写 peer 就要手工维护 21 条范围；组件是拿来改的，包进去只能 patch-package 或 fork，和你原话「集成进去再微调」正面冲突。
- 不要用 submodule / clone 整库进项目。C 里唯一正确的东西是「用 git」，那在 P0-1 已经拿到了。为了用 3 个效果把 139 个组件 + prompts + playground 塞进 Electron 仓库、再写 asar 排除规则、改一行要在 submodule 里 commit 然后回主仓库 bump 指针——这套仪式对单人自用是纯负担。更实际的坑是它给 AI 提供了一条看起来能用的捷径：直接 import '../vendor/react-bits/...'，编译得过、跑得起来，然后「微调一下」就把所有项目共享的那份改了。
- 不要做通用补丁层，不要为了修 bug 去动 components/。保住「与上游字节一致」这条规则，它是重跑管线能干净覆盖的唯一前提。LetterGlitch 那个 rAF 泄漏走 known-issues.json 打警告，你在下游改两行就行。
- 不要自动替换外链默认值，不要自动跑 npm install。都只打印，让你决策。自动装会在 taptv 这种 React 18 + three 0.184 的宿主上装出冲突版本，而这类冲突是静默的、事后极难定位。
- 不要给 CLI 做交互式 TUI、fuzzy search、shadcn 那套 registry.json 协议或 registry 服务。选型入口 playground 已经很好了（搜索 + 实时预览 + 自动参数面板 + 复制按钮），CLI 只需要 add <名字> --to <路径> 一个动词。
- 不要现在建私有 GitHub 仓库、不要往 Mac mini 同步这个目录。跨机器分发只对 npm 包方案才是硬约束，A 方案下 CI 拉的是 taptv 自己的代码。真有第二台机器要用时再说，别为一个假需求先付维护成本。
- 不要把 139 个组件拆成 139 个小包，不要给这个库维护版本号 / CHANGELOG / 发版流程。使用者一个人、下游基本一个项目，版本号是纯仪式感。
- 不要重写 buildPrompt()（scripts/build-prompts.mjs，照抄上游 TabsLayout.jsx:63-118，连空行都不能动）。也不要为了「修正 prompt 里的错误依赖行」去改 prompts/ 的内容——那份是上游文档的字节级镜像，正确的依赖数据放 index.json 的 realDeps 字段，两者各司其职。
- 整个 P0+P1 的预算是一天，不要超。超了说明在做不该做的事。
