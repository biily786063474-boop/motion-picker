能不能把 ReactBits 全站效果的
「Copy Prompt」内容全抓下来？

能，而且不需要爬网页、不需要开浏览器、不需要碰剪贴板。Copy Prompt 是纯前端在本地拼字符串，没有任何后端接口——把拼字符串的那段逻辑在本地重跑一遍就行。

日期 2026-07-31 目标站 reactbits.dev 组件量 139 个 × 4 变体 关键证据 TabsLayout.jsx:63

VERDICT

结论：走「离线复刻」，不要走「浏览器抓剪贴板」

四条路都验证过可行性，推荐 A。B 作为省事的降级选项，C 只当校验用，D 是「不落库」的另一种活法。

裁 决

方案 A · 离线复刻 buildPrompt：克隆 DavidHDev/react-bits，用 Node 脚本把 TabsLayout.jsx 里那个 buildPrompt() 函数原样搬过来，喂入仓库里现成的 codeObject 与 propData，批量吐出 139 个（或 556 个变体）prompt 文件。字节级等价于点按钮拿到的内容，一次跑完约几十秒，无反爬、无速率限制、可复现、可 diff。

HOW IT WORKS

原理拆解：那段 prompt 到底是从哪来的

这一节是全篇的地基。搞清楚它，就知道为什么「抓剪贴板」是绕远路。

reactbits.dev 是一个 Vite + React 的纯静态 SPA（Cloudflare 托管）。点 Copy Prompt 时发生的事，全部在浏览器内存里完成：

# src/components/common/TabsLayout.jsx
handleCopyPrompt()
  ├─ codeObject   ← src/constants/code/<类目>/<名>Code.js（构建时 ?raw 内联进 bundle）
  ├─ propData     ← src/demo/<类目>/<名>Demo.jsx 里的 propData 数组
  ├─ lang/style   ← 右上角 JS/TS · CSS/Tailwind 开关
  ├─ injectPropsIntoCode()  ← 把你在预览区调过的参数塞回 usage 示例
  └─ buildPrompt() → navigator.clipboard.writeText(...)
       纯字符串拼接，零 fetch，零后端

buildPrompt 的输出骨架

固定七段，顺序恒定，来源明确：

段落内容数据来源
标题## Integrate the <Orb /> component from React Bits路由 subcategory 转 PascalCase

一个必须知道的细节

injectPropsIntoCode() 只在你手动改过预览区参数时才改写 usage。默认状态下拿到的 prompt 与 codeObject.usage 原文一致——这意味着离线复刻在默认态下能做到字节级相同，不是「近似」。

OPTIONS

四个方案与取舍

按「保真度 × 成本 × 抗改版能力」三轴排。没有一个方案在所有轴上都赢，选哪个取决于你要拿这批 prompt 干什么。

方案做法保真度Props 表成本抗站点改版产出
A 离线复刻
推荐		 克隆仓库 + Node 脚本重跑 buildPrompt 字节级等价 完整 脚本约 150 行，跑一次 <1 分钟 中（跟的是仓库结构，不是站点 DOM） 556 个 .md，可全变体
B registry 拼装 直接拉 reactbits.dev/r/*.json（jsrepo / shadcn 注册表，556 个文件公开可取） 约 80% 缺 最低，一个 curl 循环 高（这是对外契约接口） 源码 + 依赖，无 props / 无 usage
C 浏览器自动化 Playwright 逐页点 Copy Prompt，读剪贴板 100%（定义上就是它） 完整 139 页 × 4 变体 = 556 次交互，需授权剪贴板权限、处理 WebGL 预览卡顿 低（改个按钮就崩） 同 A，但慢两个数量级
D 不落库 官方 MCP（npx shadcn@latest mcp init）或直接喂 reactbits.dev/llms.txt（24KB 全组件索引） — 按需 近乎为零 高 没有本地库，用时现取

取舍说明

  • A vs C：C 是「正确定义」，A 是「等价实现」。C 唯一的优势是不依赖我对源码的阅读正确——所以正确用法是用 C 抽检 3~5 个组件去校验 A 的输出，而不是用 C 跑全量。
  • A vs B：B 拿的是官方对外接口，长期最稳，但 registry JSON 里只有文件内容，没有 props 表、没有 usage 示例、没有集成指令——而这三样恰恰是 prompt 相对于「裸源码」的全部增量价值。B 单独用会退化成「代码搬运」。
  • A vs D：如果目的只是「写代码时让 AI 用上这些效果」，D 才是正解，根本不需要抓。A 的价值在于离线可检索的资产库——能 grep、能按依赖分类、能做自己的选型索引、站点挂了也在。这就是「资产收集」目录该有的形态。
  • A+B 混合：用 A 的 propData / usage / 集成指令 + B 的源码，能让源码部分永远跟线上一致而不必重新克隆 47MB 仓库。代价是多一层拼装逻辑，收益不大，不建议第一版就做。
保留的反对意见

「A 是二次实现，会跟官方漂移」——这是对的。buildPrompt() 是站点内部函数，作者随时可以改模板措辞、加段落、换 props 表格式，而你的脚本不会自动知道。

应对不是放弃 A，而是：① 脚本里记下复刻自哪个 commit；② 每次重跑前 git log 看 TabsLayout.jsx 有没有动；③ 保留 C 的抽检脚本作为「对账工具」。把漂移变成可检测的，而不是假装不存在。

RECOMMENDED

方案 A 的管线设计

下面是给「工匠」角色的实现说明书，不是代码。四步，每步的输入输出都已验证存在。

STEP 1 · 取料
克隆仓库到本地缓存目录
codeload.github.com/DavidHDev/react-bits/tar.gz/refs/heads/main，47MB，含 4 套变体源码。记下 commit SHA 写进产物元数据。
STEP 2 · 解析 codeObject
139 个 src/constants/code/*/*.js
每个文件形如 import code from '@content/…/Orb.jsx?raw' 加 export const orb = {…}。不要用 esbuild 直接跑它（?raw 是 Vite 专属语法）——按 import 语句解析出别名路径，直接从 src/content | tailwind | ts-default | ts-tailwind 读对应文件即可。usage / dependencies 是模板字符串，正则或轻量 AST 都能取。
STEP 3 · 解析 propData
139 个 src/demo/*/*Demo.jsx
已核实：139/139 全部写作 <PropTable data={propData} />，且 propData 都是 useMemo(() => [ …字面量数组… ], [])。用 @babel/parser 取 AST 抓那个 ArrayExpression 最稳；纯正则也能过，但遇到描述里带反引号或大括号会脆。这是全流程唯一有技术风险的一步。
STEP 4 · 复刻 buildPrompt 并落盘
照抄 TabsLayout.jsx:63-118
连空行和 --- 分隔符都照抄，包括那个「有 CSS 时步骤编号 3/4/5、没 CSS 时 3/4」的分支。输出到 prompts/<类目>/<组件>-<LANG>-<STYLE>.md。

变体策略：先只出一套

556 个文件里有大量重复（同一组件的 4 个变体，差异只在源码块）。建议 第一版只生成 TS-TW 一套（139 个，约 1.6MB），需要别的变体时再补——4 套全出约 6.5MB，索引和去重成本都上来了，收益却只在「你恰好用 JS+CSS」的场景。

体量提醒

单个 prompt 平均 11~14KB，约 3~4k tokens。整套 139 个约 50 万 tokens，不可能整体塞进上下文。所以 index.json 不是可选项，是必需品——检索靠索引，命中后才读具体那一个 .md。

RISKS

风险与边界

合规、技术、维护三类，都有明确应对。

许可证 低风险

react-bits 是 MIT 开源，组件本就设计为 copy-paste 使用，仓库里明确提供 CLI 安装与 llms.txt 供 AI 消费。做本地资产库属于预期用法。但要保留原始版权声明、别去掉出处；这批产物是自用素材库，不要当自己的作品对外分发。

技术风险点 1 处

只有 STEP 3 的 propData 解析可能翻车（描述文字里的特殊字符）。验收标准：139 个文件全部解析出非空数组，任何一个为空都算失败，不许静默跳过。

网络 注意

本机 Clash TUN 全局接管。47MB tarball 下载若卡住，先按代理排障套路查链路，别怀疑 GitHub。本次调研中该下载走通了（47MB 正常完成）。

维护 季度

react-bits 更新频繁（139 个组件仍在增长）。脚本设计成幂等可重跑，靠 .meta.json 的 commit SHA 判断是否需要重跑，重跑后 diff 就能看出上游加了什么组件。

明确不做的事

  • 不做全站 HTML 爬取——SPA 渲染，爬到的是空壳，纯属浪费。
  • 不做剪贴板监听或劫持——没必要，且脏。
  • 不为「更保真」而上 Playwright 跑全量——556 次带 WebGL 预览的页面交互，跑一小时换来和 A 一样的结果。
