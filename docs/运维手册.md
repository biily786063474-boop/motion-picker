# 运维手册

日常怎么维护这个库，以及出问题时按什么顺序排查。

---

## 定期要做的

### 同步上游（建议一季度一次）

```bash
npm run sync      # fetch-repo → build-prompts → index-custom → build-semantic
```

**这条命令是安全的**：全部生成到 `.tmp-build/`，只有 139 个组件全部解析成功才原子替换；中途任何失败一个字节都不落盘。跑完会打印新增/删除了哪些组件。

同步之后**必须做两件事**：

```bash
node scripts/verify-against-site.mjs    # 与线上 Copy Prompt 逐字节对账
git diff --stat                          # 看这次到底动了什么
```

对账失败意味着上游改了 `buildPrompt()`，本地的复刻漂移了 —— 见下面「上游改了 buildPrompt」。

`custom/` 不受影响，`index-custom` 会自动把自有组件重新合并回索引。

同步还会带来第三件事：**新组件没有语义卡片**。`build-semantic` 会把它们算进索引，
但只有客观特征（作用面/触发/技术），没有中文描述，语义检索基本命不中。跑完看这行：

```
中文语义  70/140（缺的靠英文关键词兜底，检索质量会差）
```

补的办法见下面「补语义标注」。

### 补语义标注（同步引入新组件之后）

语义层分两半，分开存是有原因的：

| | 存在哪 | 谁生成 | 重跑管线会怎样 |
|---|---|---|---|
| 客观特征 | 不存，每次现算 | `lib/traits.mjs` 从源码 AST 推 | 重算，永远和源码一致 |
| 中文语义 | `prompts/semantic-annotations.json` | AI 看巡检截图标注 | **保留**，不会被冲掉 |

所以标注是一次性投入，同步上游不会丢，只需要给**新增的那几个**补。

前置条件：得先有截图，`.cache/shots/all/<组件名>.png`。没有就先 `npm run sweep`。

补的时候把这些材料给标注者（AI agent 或你自己）：

- 截图 `.cache/shots/all/<名字>.png` —— **主要依据**，组件名基本没有语义
- 客观特征（`prompts/semantic.json` 里对应条目的 `surface` / `triggers` / `tech` / `heavy`）
- 参数表 `prompts/props.json`、源码 `components/<类目>/<名字>.tsx`

字段规范和写法要求见 `docs/组件入库标准.md` 的「关于 `semantic`」一节。有三类要特别小心：

1. **截图全黑的光标类**（`surface: cursor`）—— 静态截图必然拍不到鼠标驱动的效果，
   得读源码判断它画的是什么，别因为图黑就写「暗色背景」。上一轮 16 个光标类组件全踩这个坑，
   是靠复核阶段捞回来的。
2. **包裹型**（`surface: wrapper`）—— 图里那块卡片/文字是预览容器塞的占位内容，不是组件本身。
3. **文字类**（`surface: text`）—— 描述文字怎么动（逐字？打字机？故障闪烁？），不是文字写了什么。

写完汇总进标注文件再重建索引：

```bash
node scripts/collect-semantic.mjs <workflow 目录>   # 从 journal.jsonl 提取，可传多个目录
npm run semantic                                    # 合并进 prompts/semantic.json
node scripts/add.mjs --find "<新组件的典型需求描述>"  # 搜得到才算过
```

`collect-semantic.mjs` 会把描述太短、缺 `keywords` 的挑出来警告。手工写的标注直接编辑
`prompts/semantic-annotations.json` 也行 —— 它是这一层的唯一真源。
**自有组件不走这条路**，直接写在自己的 `meta.json` 的 `semantic` 块里，优先级更高。

### 全量巡检（改过 playground 之后）

```bash
npm run sweep              # 139 个组件逐个渲染 + 截图，约 10 分钟
npm run sweep:offline      # 断网模式，验证离线可用性
npm run check:blank        # 像素级空白检测（"不报错" ≠ "看得见"）
npm run check:network      # 有没有组件在偷偷请求外网
```

**巡检跑的时候不要改 playground 代码。** dev server 热更新会让正在跑的巡检拿到中间态，整批结果作废——这个坑踩过，一轮 10 分钟白跑。

### 回归测试（改过 CLI / 核心逻辑之后）

```bash
npm test                   # 14 项冒烟，不装依赖也能跑
npm run verify:playground  # 选型台交互回归
npm run verify:remount     # 调参闪烁检测
```

## 排障：按这个顺序来

### 第一步永远是体检

```bash
npm run doctor
```

它按三层报告：**取用组件**（几乎不需要环境）/ **选型台**（需要 npm install）/ **skill 接线**。
**只有核心层没过才是真问题**，选型台没就绪不影响取用。

### 症状 → 原因

| 症状 | 先查 |
|---|---|
| 组件在项目里没样式，控制台干净 | 宿主没装 Tailwind。95/139 个组件带 Tailwind 类 |
| `npm i @react-three/*` 被拒绝 | 宿主 React 18。fiber v9 的 peer 写死 `react >=19` |
| 组件白屏但不报错 | 必填 prop 没传，或默认值里的外链挂了 |
| 拷进去 500 / `Unexpected token '<'` | 资源没跟着走。用 `--dry-run` 看清单 |
| 选型台整页点不动 | 某个组件注入的全局 style 撞了 `.pg-*` 之外的类名 |
| 调参数时画面闪 | 重挂太频繁。跑 `npm run verify:remount`，正常应只有 0~1 帧 |
| 某组件报错但它自己没问题 | 前一个组件卸载不干净。用 `verify-isolated.mjs` 隔离验证 |
| 端口被占 | `PORT=5199 npm run dev` |

### 隔离验证：区分「它自己的问题」和「被前一个连累」

```bash
node scripts/verify-isolated.mjs Lightfall
```

巡检是顺序切换 139 个组件的，上一个卸载不干净（残留 rAF、没清的定时器）会把错误算到下一个头上。
这个脚本每个组件开一个全新浏览器，杜绝串扰。

**实战**：`Lightfall` 在巡检里一直报 `null.getBoundingClientRect`，隔离测试完全干净——真正的问题在它前一位 `LetterGlitch` 的清理函数里。

## 特殊场景

### 上游改了 buildPrompt

`scripts/build-prompts.mjs` 里的 `buildPrompt()` 是照抄上游 `TabsLayout.jsx:63-118` 的，连空行和步骤编号分支都一样。上游改了措辞或结构，本地就会漂移。

发现方式：`node scripts/verify-against-site.mjs` 对账失败。

处理：
1. 看上游那个函数改了什么（`.cache/react-bits-main/src/components/common/TabsLayout.jsx`）
2. 同步改本地的抄本
3. 重跑 `npm run sync` + 对账，直到 3/3 一致

**别自作主张"优化"那个函数**，它的价值就在于与线上字节一致。

### 上游改了仓库结构

管线硬依赖上游的目录布局：`src/demo/<类目>/<名>Demo.jsx` 里的 `propData` 必须是纯字面量数组、`src/constants/Categories.js` 的 `CATEGORIES` 必须是字面量。

上游改了结构 → `build-prompts.mjs` 会成片失败并非零退出，**产物不会被破坏**（原子写保护）。
处理：读报错信息，改 `parseDemo()` 的解析逻辑。

### 组件依赖版本冲突

比如 `three` 升到不兼容的大版本：

```bash
npm run check:deps      # 扫全部源码的真实 import，验证能否解析
npm run sweep           # 看哪些组件挂了
```

`ModelViewer` 引用的 `three/examples/jsm/loaders/OBJLoader` 在 Node 严格 ESM 下解析不了（three 0.180 的 exports 要求带 `.js` 后缀），但 vite 能解析，运行时没问题——这类「工具报错但实际能跑」的要分清。

### 加了自有组件之后

```bash
npm run validate        # 先过标准
npm run index:custom    # 合并进索引
npm run semantic        # 合并 meta.json 里的 semantic 块，让它能被检索到
npm run dev             # 选型台里看效果
```

详见 `docs/组件入库标准.md`。

## 发布

推 GitHub 之后 CI 会自动跑：Node 18/20/22/24 × Ubuntu/macOS/Windows 共 12 个组合的冒烟，外加一个选型台构建。

**CI 的冒烟矩阵刻意不跑 `npm install`** —— 取用路径零依赖可用是核心性质，改坏了立刻红。

维护工具（`validate` / `index-custom` / `build-prompts` / `sweep`）需要依赖，走单独的 job。
往 `add.mjs` 或 `add-core.mjs` 里加第三方 import 会破掉这条边界。

发版前手工确认：

```bash
npm test                              # 本地冒烟
node scripts/verify-against-site.mjs  # prompt 保真度
node scripts/add.mjs --find "暗色流动的背景"   # 语义检索没退化
npm run build                         # 选型台能构建
git status                            # 没有该提交而没提交的
```

演示动图重录（改过选型台 UI 之后）：

```bash
npm run dev
node scripts/record-demos.mjs          # 8 个组件效果
node scripts/record-demos.mjs --flow   # 工作流演示
```

用动态 WebP 不用 GIF——同画质体积小一个数量级（Silk 从 10MB 降到 0.97MB）。

## 目录职责

| 目录 | 谁维护 | sync 会不会动 |
|---|---|---|
| `components/` | 生成物，上游镜像 | **整目录替换** |
| `prompts/` | 生成物 | **整目录替换** |
| `custom/` | 你手写 | 不碰 |
| `public/` | 混合（上游资源 + 手工放的 draco） | 逐文件合并，不删 |
| `playground/` | 你手写 | 不碰 |
| `scripts/` | 你手写 | 不碰 |
| `skill/` | 你手写 | 不碰 |

**`components/` 里发现的 bug 不要就地改** —— 下次 sync 会被覆盖。记进 `scripts/known-issues.json`，取用时会打警告，让使用者在自己项目里改。

这条规则保住了「重跑管线 = 干净覆盖」这个性质。破了它，每次同步都是笔糊涂账。

## 关键文件

| 文件 | 作用 |
|---|---|
| `prompts/index.json` | 检索索引 + 取用元数据（真实依赖、资源、外链、导出形式） |
| `prompts/props.json` | 结构化 prop 元数据，选型台参数面板的数据源 |
| `prompts/semantic.json` | **生成物**，语义检索索引（客观特征现算 + 中文语义合并） |
| `prompts/semantic-annotations.json` | 中文语义层的**唯一真源**，AI 标注产出，重跑管线不会丢 |
| `prompts/.meta.json` | 上游 commit、生成时间 |
| `playground/preview-overrides.json` | **机器生成**，别手改，会被覆盖 |
| `playground/registry.jsx` 的 `OVERRIDES` | 手写特例，放这里 |
| `scripts/known-issues.json` | 已查清但没修的问题，取用时会提示 |
| `.rb-context.json` / `.rb-selection.json` | skill 与选型台之间的桥，gitignore |
